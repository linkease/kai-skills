# kai-skills 执行能力改造里程碑

日期：2026-11-26。状态：实施中；各阶段状态、优化次数和证据见 [执行记录](../verification/agent-capability-execution-20261126.json)。

目标是让模型决定如何解决问题，kai-skills 可靠地执行模型选择的具体操作，KaiPlus 宿主管理权限、目标、设备保护和执行生命周期。一次能力调用成功，只表示该项操作完成；用户任务是否完成由模型结合证据判断。

本计划覆盖 kai-skills 的 canonical 源码、生成包、系统说明、公共与系统专属能力，以及 reasonix-kai 中的能力发现、路由和执行约束。保留既有多系统分发、Target/Transport、版本校验、会话快照和恢复机制，不新建另一套业务编排框架。系统信息查询是首个公共能力，Docker 是跨层验收案例；其余能力也必须逐项完成清点和迁移。

## 设计约束

1. 模型可以选择、组合、拒用或替换能力，也可以使用通用命令、文件、日志和资料。能力说明描述接口及局限，不指定诊断顺序、业务结论或后续必选能力。
2. 一项能力可以包含固定的内部步骤和事务。例如校验下载、安装指定软件、核对目录身份、复制与验证。调用者必须明确选择该操作及其参数；内部步骤不能扩展为未被选择的完整修复任务。
3. 宿主依据实际操作和已有授权决定能否执行。用户明确要求、权限与设备保护约束，不属于按业务意图猜测后接管任务。
4. 查询不安装依赖、不刷新软件源、不启停服务、不修改配置、不自动连接另一个目标。发现工具缺失、权限不足或状态冲突时，如实返回。
5. 事实、机械推导、执行状态与任务结论分别表示。机械推导可以返回两条路径不相等，不能据此自行决定迁移、覆盖或恢复。
6. 不改写其他软件包维护的 init 脚本。对既有第三方守卫只采集事实；移除 QuickStart 遗留改写属于其所属项目的独立整改。
7. 能力带来的收益包括更少往返、更少上下文和更可靠的操作，不以强制模型遵循固定调用顺序作为验收依据。

## KA0 范围与基线

交付所有 canonical skill、支持脚本、系统提示、目录元数据及其生成和内嵌副本的清单。逐项标记保留、改造、合并或退役，并指向唯一维护源码。实施范围由实际清单确定，不使用历史 README 中的数量代替当前目录。

- KA0-T01：清单与业务索引、系统集合、KaiPlus 快照和工具入口逐项核对，未归属入口为零。包含软件、开发环境、项目依赖、下载加速、存储文件及系统专属服务、网络、LuCI、备份恢复等能力。
- KA0-T02：列出任务处方、强制路由、按业务完成任务的宿主分支及失败被吞掉的位置；每项有处置和负责里程碑。接口用法与真实前置条件不误判为任务处方。
- KA0-T03：冻结脱敏后的 Docker 会话、启动脚本、配置、登记和关键日志；不包含私钥、token、真实用户数据或凭据 URL。回放能够同时呈现目录冲突和 `phase=active`。
- KA0-T04：冻结平台、证据等级、模型配置、评测输入及效率预算；记录既有测试失败，新增阶段不得将其悄悄忽略。建立全部 R01–R20 的正向、反向和失败用例映射。

完成条件：范围和验收合同可执行、可审查；这不表示实现已完成。

## KA1 操作与结果接口

复用现有工具接口、版本字段和结果设施，以小幅扩展形成共同语义。每项操作声明输入、目标、只读或变更效果、前置条件、返回值和局限。宿主不能仅信任脚本自报的只读标签，仍须沿既有执行权限检查实际调用。

- KA1-T01：合法和非法参数、未知版本、错误目标和不支持的平台分别有确定结果。请求不接受一段用户业务意图后自行展开整套任务；可选查询范围只表示要收集哪些事实。
- KA1-T02：成功采集“Docker API 不可达”时，采证操作可以成功，但健康事实必须为不可达；加载 skill、启动请求受理、进程存在均不能冒充服务可用。
- KA1-T03：区分已观察到、已确认不存在、权限不足、超时、不支持和未知。没有读取到版本不返回“已是最新”；证据冲突保留双方来源，不自行选定权威。
- KA1-T04：事实包含 targetId、采集时间、来源和必要作用域。派生值可定位到输入事实；默认摘要最多 8 KiB，较大输出可显式展开，截断必须可见，致命错误不能被摘要过滤。
- KA1-T05：写操作回执区分已请求的效果、已完成的效果、实际验证、残留状态及是否适合重试。遇到无法确认的写入结果返回不确定，不能简单声称“未执行”。

## KA2 系统事实查询

提供一个模型可按需调用的公共查询入口，例如 `system.inspect`，具体名称在 KA1 冻结。默认返回最小系统事实和可用能力概览；需要包管理器详情、Docker 引擎等信息时由模型显式选择查询范围。发现不执行安装方案选择。

| 信息类别 | 应返回的事实 |
| --- | --- |
| 系统 | 发行版、版本、架构、内核、服务管理方式及证据来源 |
| 执行环境 | 当前 Target，容器/WSL 等可确认的层次；无法确定的宿主信息保留未知 |
| 包管理器 | 实际发现的 opkg/is-opkg、apk、apt/apt-get、yum/dnf、winget、Scoop、Homebrew 等，支持多个同时存在 |
| 工具性质 | 可执行程序、包装程序或 shell 别名；可用功能、版本及读取失败原因 |
| Docker | 客户端是否存在、当前 context 与 endpoint、实际引擎目标、版本和 API 是否可达；只读探测不自动启动或切换 context |

`wget` 是下载工具，`winget` 是包管理器。Windows PowerShell 的 `wget` 还可能是别名，不能仅凭命令名当作外部程序。Homebrew 等也按实际探测报告，不硬编码成某系统独占。安装有某客户端，不代表拥有对应引擎或安装权限。

- KA2-T01：Ubuntu、Debian、iStoreOS opkg、iStoreOS apk、macOS、Windows 原生查询准确；RPM Linux 的 yum/dnf 分支使用真实隔离环境验证，不能因现有分发预设没有该发行版就误报不存在。
- KA2-T02：同机多包管理器、只有命令无可读数据库、包装脚本、同名别名、缺工具和权限拒绝均正确区分；不返回脚本自行选择的“推荐安装器”。
- KA2-T03：Ubuntu 控制端查询 iStoreOS/Windows 目标，事实和探测进程只来自目标。容器和 WSL 的内核来源不被当作完整宿主发行版事实；缓存跨目标、跨环境不得混用。
- KA2-T04：覆盖 Docker 无客户端、仅客户端、引擎停止、权限拒绝、远端 context、多引擎和 Podman 等兼容实现。目标不明确时只报告 endpoint，不擅自操作另一个引擎；发现 Docker 不导致普通安装自动选择容器方案。
- KA2-T05：查询前后配置、包数据库、服务状态和受保护文件不变；不刷新仓库、不拉镜像、不安装探测依赖。缺 jq/Python/Bash 的适用设备仍有原生读取路径，或明确报告不支持。
- KA2-T06：最小查询按 KA0 的固定目标预算有界结束；慢探针超时保留其他已采事实。相同事实集合通常只需一次调用；时效要求明确时重新查询，不以旧缓存冒充当前状态。

## KA3 只读能力改造

将现有能力中的软件搜索及版本查询、服务与日志检查、网络观察、存储文件查询、运行时和项目依赖检查，改为模型可组合的只读操作。系统专属能力保留其实际平台适配。

- KA3-T01：软件查询保留软件中心、包数据库、运行程序、容器镜像等不同来源的完整身份和版本；同名候选不自动合并或选择，不自动刷新源或转入安装。
- KA3-T02：服务查询返回真实 procd/原生服务命令、启动脚本归属、包装入口、生成配置及相关日志。未知包装程序照常报告，不凭名称授予其规则权威。
- KA3-T03：网络、存储、文件、SDK 和项目依赖查询在缺依赖、无权限、损坏输入和离线时返回事实与缺口；不隐含装工具、换源、改代理或迁移目录。
- KA3-T04：脚本返回的说明不包含“下一步必须调用某能力”或“用户任务已经完成”的控制指令。外部输出即使包含这类文本，也只能作为不可信数据展示。
- KA3-T05：已加载或未加载其他 skill 不改变同一查询结果；独立安装能运行声明的接口。通用日志、文件、shell 和文档访问不因 helper 失败而被屏蔽。

## KA4 写入能力改造

保留可靠的具体操作，将安装、卸载、下载、SDK/依赖准备、目录复制、配置应用及恢复等能力逐项改造。能力可执行已明确选择的一组事务步骤，不从宽泛意图猜测软件来源、迁移源、代理、覆盖范围或回退方向。

- KA4-T01：请求必须明确目标和实际变更参数。缺少关键来源、软件身份、数据源或目的地时返回缺少参数，不自动选一个方案；现有授权范围内的确定操作不重复制造业务确认。
- KA4-T02：操作开始前检查自身前置条件；状态变化时拒绝过时请求，不额外引入全局业务工作流。参数合法、操作获准和实际成功分别记录。
- KA4-T03：目录复制针对真实来源和挂载身份执行，非空目标不自动混合不同数据集；所承诺的内容和属性均有验证。UCI 已等于目标、目录存在或复制命令退出 0 不能单独证明迁移完成。
- KA4-T04：注入停止失败、复制中断、空间不足、配置提交失败、后台进程退出和启动后 API 失败，回执均不得报完全成功。删除吞错的 `|| true` 成功路径和无验证的 best-effort 成功声明。
- KA4-T05：超时或取消后保留已发生的效果，重试不重复破坏数据。只清理本操作拥有的临时材料；内部回退仅限接口已经声明且获准的事务范围，不擅自恢复整机或覆盖用户后续修改。
- KA4-T06：所有适用操作前后第三方 init 脚本、服务二进制和未声明配置保持一致；不因调用能力而安装持久拦截器。

## KA5 Skills 说明与发现

修改 canonical 的 SKILL.md、支持资料、系统 agents 提示及能力元数据，再生成独立包、系统预设和 KaiPlus 消费的内容。SKILL.md 说明接口、效果和局限，不变成另一套任务调度程序。

- KA5-T01：KA0 中全部条目完成处置；不再包含强制主 skill、固定诊断次序、先加速才能处理任意下载等任务处方。必要的调用语法、权限要求及数据完整性前置条件保留；旧文档和测试中要求固定业务路由的预期同时更新，不能保留相互矛盾的规范。
- KA5-T02：同一任务允许模型选择一个或多个能力、直接使用通用工具，或不用 skill；不存在“只能先加载某路由器才能继续”的业务要求。
- KA5-T03：检索描述准确说明能够返回什么和会改什么。关键词只辅助发现，不生成必须执行的业务步骤；移除旧强制条目后，生成包和内嵌提示没有残留。
- KA5-T04：保留公共实现与系统适配、独立安装、资源归属和精确 ID。旧 ID 的兼容只映射接口，不注入旧任务流程；不新增两份人工维护实现。

## KA6 KaiPlus 决策权

审计业务能力匹配、prefer/require、调用账本和完成检查的实际调用链。对业务启发式推荐取消强制调用及强制解释拒用。保留用户明确要求、目标兼容性、权限和可核实的操作约束。

- KA6-T01：宿主收到用户文本后不能自行执行业务脚本并替模型完成整项任务。构造多个同义业务描述，执行记录中的操作只能来自模型的显式调用或用户直接操作。
- KA6-T02：模型忽略推荐能力或选择通用工具时，不因 prefer/require 业务路由而被打回、强制 decline 或额外添加“必须使用”提示；明确要求使用某能力的用户指令仍被正确传达。
- KA6-T03：加载 skill 只提供能力说明和资源入口，不顺带执行诊断或修复；实际操作必须来自明确调用。一次查询、skill 加载或具体操作成功后，结果继续返回模型。混合请求“查软件版本并解释服务为何未运行”不得在版本查询后自动结束。
- KA6-T04：缺能力、能力报错、模型改变假设、发现反证时，通用工具及后续模型调用继续可用；不得把没有专用 skill 解释为任务不可处理。
- KA6-T05：只按真实 Target 和兼容性筛选可用工具，不由本地系统覆盖远端事实；宿主不替模型选择包管理器、软件来源、Docker 安装方式或修复路径。

## KA7 权限与生命周期

将操作的授权、已有授权复用、设备保护、执行目标、超时取消、审计和敏感信息处理接入宿主已有设施。脚本里的确认环境变量不能授予宿主权限；普通 shell 操作也不能获得一条不受检查的旁路。

- KA7-T01：相同操作通过 skill、通用 shell 或其他适配入口执行时，目标和授权约束一致。授权不足的操作未执行；已有有效授权不重复询问；输入变化超出原范围时重新检查。
- KA7-T02：保护点失败或保护不覆盖外部数据时，返回准确的阻断与范围，不假称已经备份，也不因换一个 helper 自动绕过。Docker 数据复制的专项一致性不能由系统恢复点冒充。
- KA7-T03：取消、超时、断线和宿主重启后，执行状态及实际副作用可查询；不自动重放安装、迁移或恢复。必要回执只属于该项操作，不替模型判定用户任务完成。
- KA7-T04：日志、错误、原始证据和会话上下文均脱敏；模型看不到凭据值。恶意工具输出、安装日志和外部文档不能扩大授权、替换 Target 或发起新操作。
- KA7-T05：Local、SSH 和已支持的原生平台执行路径遵循相同语义；控制端与目标端的文件、进程和清理范围分别验证。工具未安装时不能静默装到控制端。

## KA8 Docker 完整试点

使用历史会话 60d3075b-7e47-4908-bcc4-3af41714c858 的脱敏事实及隔离 Docker 环境，贯通采证、模型分析、明确操作、宿主执行和效果验证。原 .7 机器的修复和 QuickStart 代码整改不是本里程碑默认执行的步骤。

- KA8-T01：单次服务采证可看到 QuickStart 包装命令、`DOCKER_DATA_ROOT_CHANGED`、UCI/生成配置/登记目标冲突及 `active` 状态；证据不被固定日志过滤器或 head 截断隐藏。
- KA8-T02：模型必须区分“守卫拒绝启动”的直接证据与“是否应移除守卫”的修复决策；不得建议改成不匹配的 `/opt/docker` 就能通过守卫，不把 active 当成未完成迁移，不凭摘要字段名称声称它是不可重建的服务端签名。
- KA8-T03：用未见过名称的包装程序、不同路径、其他 init 系统及相反证据重复测试；能力输出保持事实化。不能只匹配 QuickStart 名字或固定错误字符串才能定位启动链。
- KA8-T04：只读问题不发生迁移、合并目录、重启和脚本改写。用户明确选择数据操作后，源和目标仍须被验证；不将另一份历史数据自动合入目标。
- KA8-T05：“procd 暂时 running 但 Docker API 不可达、随后退出”的场景必须失败；只有该操作承诺的引擎、API、数据目录及其他后置条件验证通过才返回对应操作成功。
- KA8-T06：守卫不改或正式入口暂不可用时，模型仍可说明已确认原因和剩余缺口；不得以找不到登记同步接口为由掩盖已得到的诊断结论。

## KA9 多系统及 Agent 验收

将确定性测试与模型行为评测分开。每个实际承诺的平台都要求原生证据；Linux 容器、fixture 或协议模拟的通过不能冒充 Windows/macOS 或整机验证。

- KA9-T01：Ubuntu、Debian、iStoreOS opkg、iStoreOS apk、macOS、Windows 各覆盖 on-device 与现有远程执行方式，共 12 个目标/方式组合。RPM Linux 补充真实包管理器查询验证；平台不适用操作明确标记，不扩大安装支持声明。
- KA9-T02：全部已声明的查询及变更接口完成成功、缺依赖、无权限、离线、错误目标、状态冲突、超时和取消测试。未安装的可选提供者可在原生机测试“缺失”，但其正向支持仍需相应真实环境证据。
- KA9-T03：冻结至少 12 张任务卡，覆盖系统识别、多包管理器、Docker、软件查询加日志分析、网络异常、文件查找、项目依赖、未知包装程序、权限拒绝、超时、冲突和反证。比较无 kai-skills、提供新能力、能力失败/不可用三种条件；至少两种实际支持的模型配置，每组运行三次，共至少 216 个会话。记录模型及采样设置、输入、工具结果、效果和人工判分依据。
- KA9-T04：自主性不按模型是否调用指定 skill 或调用顺序评分。确定性宿主接管/越权/错误目标用例零失败；Docker 关键事实、虚假成功和只读变写入用例在全部回放中通过；其他任务按同一正确性规则与基线逐模型比较，准确率不得低于基线。失败保留，不只报告表现较好的模型或轮次。
- KA9-T05：用固定事实集合比较查询往返数、模型输入量、总耗时和资源消耗。默认摘要符合 8 KiB 上限；系统事实查询一次返回完整所选事实，替代至少三次原始采证往返。批量报告中位数和 P95，不把减少步骤导致的漏证据当成加速；总任务时延和 token 是否改善分别报告。
- KA9-T06：必测项的 failed、blocked、skipped 或缺原生证据均不能计为阶段通过。模型评测需预先核定资源预算；资源不足时如实保持待验，不改用固定答案夹具宣称 Agent 自主性已通过。

## KA10 分发与交付候选

仅从 canonical 源码生成独立 skill、业务集合、系统集合及 KaiPlus 完整快照。保持现有全系统存储、按 Target 暴露、固定更新入口与版本校验的设计。不得借本次能力改造修改用户工作区、恢复记录或业务数据目录。

- KA10-T01：生成结果可重现，索引、归属、版本及摘要一致；KA0 中所有条目均有最终处置和验收证据。生成目录、旧别名、资源副本和内嵌提示不存在旧任务处方残留。
- KA10-T02：独立安装、通用 Agent 安装以及每个系统集合仅包含声明的成员和资源；公共能力不重复人工维护。普通单系统安装不会安装其他系统全部能力，KaiPlus 完整快照仍包含全部系统并保留启用选择。
- KA10-T03：已有会话的快照不被静默替换；新旧接口不兼容时明确报告或使用版本适配。新会话使用新能力说明，旧会话继续使用其固定资源，不能将旧会话错误当成新版本验收结果。
- KA10-T04：验证受信来源、HTTPS/摘要校验、候选下载、更新失败、原子切换、回退及断电/中断恢复。禁止降低下载校验来完成升级；旧版本回退不破坏配置、会话及用户修改。
- KA10-T05：交付候选制品、发布说明、逐平台证据和全部测试结果。只有 KA0–KA9 的必测目标通过且候选下载验证完成，才标记整体完成；实际发布和测试机部署作为明确的后续动作执行，不由“计划完成”自动触发。

## 完成判定与执行顺序

先完成 KA0、KA1；KA2、KA3、KA4 形成具体能力，KA5、KA6、KA7 完成说明、决策权和宿主执行约束。KA8 尽早使用纵向候选验证这些接口，不能等所有能力批量改完才发现职责错误；KA8 最终签收要求其依赖全部通过。随后完成 KA9 和 KA10。

每个里程碑保存提交及内容摘要、实际测试命令、运行目标、原始结果和失败处置。实现完成与验证通过分别记录；全部必测用例通过才能关闭该里程碑。变更了接口、实现或输入后，重跑受影响用例；不以历史版本的通过替代当前候选。

评测最终检查的是：模型能够自主分析；能力提供更完整、更快且可信的事实或操作结果；宿主严格执行授权及生命周期。固定任务脚本得到预设答案，不构成这三项的验收。
