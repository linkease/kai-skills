# 业务 Skill 独立发布与系统集合：实施里程碑

日期：2026-10-30。

状态：正在按本计划实施；逐项结果见 [执行记录](../verification/business-distribution-execution.md) 和 [机器状态](../verification/business-distribution-status.json)。本文的 BM0–BM10 与历史多系统 MS0–MS10 分开编号；历史成功不直接计为新分发方式通过。

## 目标与交付边界

同一份 canonical 源码生成三种用户可选的分发单位：

1. 单个业务 skill：只下载并安装一个目录，即可完成其声明的业务任务。
2. 业务集合：例如 development、software-management，以锁定清单组合相关 skills。
3. 系统全量集合：为 Ubuntu、Debian、iStoreOS、macOS、Windows 分别提供该发行版本全部适用 skills，并支持 on-device / remote-control 两种方式。

业务 skill 是最小发布、发现、安装和版本单位；集合没有自己的 SKILL.md，不增加一个会被 Agent 当作业务技能加载的空壳入口。系统和连接方式是适配与选择条件。

首轮覆盖现有六个通用业务 skill：kai-software、kai-dev-environment、kai-project-dependencies、kai-download-acceleration、kai-storage-files、kai-tool-bootstrap。现有平台专属和 Transport skills 在 BM0 逐项盘点，全部归入明确的独立发布、兼容资源或内部资源类别，不能在生成时默默遗漏。

建议公开布局如下；具体元数据格式在 BM1 冻结：

```text
components/                 唯一维护源码及系统适配
skills/<skill-id>/          生成的、可直接复制的独立 skill
bundles/                    业务集合和系统全量集合声明/锁
platforms/<system>/<mode>/  保持兼容的十个生成预设
```

继续复用 ks-cli、zsetup、mise、linkspace 和原生包管理器。分发重构不重新实现这些工具的下载、软件解析或服务管理。Windows WinGet 集成所需变更计入 BM8；底层服务存在不等于新 skill 已通过验收。

## 已确认的实现原则

- canonical 源码维护一次。独立发布物、集合、旧 preset 和 Kai 消费层均从声明生成；不手工维护多套实现。
- skill ID 保持稳定；跨平台通用 skill 使用同一 ID 和发布内容，内含必要平台适配。平台专属 skill 的支持范围明确声明。
- 正常业务路径不能要求相邻目录中必须存在另一个 Kai skill。公共执行资源随发布目录携带，保留来源及摘要；内嵌资源不携带会被误发现的嵌套 SKILL.md。
- 代码资源依赖、可选关联业务、目标设备上的程序依赖分别声明。携带 bootstrap 资源不意味着自动安装软件或启动服务。
- 单 skill 无需先安装本仓库集合管理器，也无需 Agent 识别自定义依赖字段。直接复制目录仍可发现、阅读并执行公开任务。
- 集合锁定成员 ID、版本和内容摘要。同一 ID/version 在单 skill、业务集合、系统集合、旧预设中的内容必须一致。
- 同一 Agent skills 目录中，同一 skill ID 只保留一个实际版本。重叠选择复用相同内容；不同版本/摘要冲突必须在写入前列出受影响选择并停止，不自动升级其他集合、不隐式降级、不求解版本范围。
- 集合安装与单装分别记录选择意图。卸载只释放本次选择，仍被其他选择使用的 skill 保留。手工复制且没有归属记录的目录不自动收编或删除。
- 系统“全部”是本发行版本清单中明确适用于该系统的全部公开 skills；构建时冻结展开结果。不能在测试失败后通过删掉成员把集合改成通过。
- skill 的可安装/可发现状态、业务功能通过状态、加速证据状态和发布状态分别记录。安装成功不能替代运行成功。
- 保持 Bash 支持及 Windows 原生首次引导；Git Bash、PowerShell、WSL 和控制端/目标端继续区分。保持 iStoreOS 自带 curl、库和原生包管理策略。

## BM0 范围、清单与基线

任务树：盘点全部 SKILL.md 与兼容资源 → 追踪跨目录调用和说明依赖 → 冻结公开业务及平台矩阵 → 运行现有回归 → 建立逐项证据表。

验收标准：

1. 每个现有 skill/兼容资源都有 ID、源码路径、公开去向、支持系统、执行方式和负责人代码边界；清单数量与扫描结果一致，无未分类项。
2. 六个通用 skill 的正常流程和失败流程分别列出必需脚本、文档、相邻 skill 引用、原生程序、服务及平台资源。可选诊断不能误列为所有任务的必需依赖。
3. 冻结平台/架构范围：Ubuntu、Debian、iStoreOS 使用现有可重建实验室锁定架构；macOS arm64、Windows AMD64 使用原生目标。额外架构只按已获得的证据声明，不泛称全部架构通过。
4. 对每个通用 skill 定义一个有实际输出断言的最小独立任务；六个 skill × 五系统共 30 个 required 功能用例。平台专属 skill 按实际支持系统补充用例。
5. 保留现有生成、安装生命周期、架构、Transport、runtime 和消费者测试的基线。既有失败单列复现命令和影响；受影响的新发布门禁修好前不能通过。
6. 为每个验收点指定唯一 case ID、预期、证据等级和归属里程碑。真实测试设备、凭证、指纹与私有日志位置通过仓库外配置传入。

交付证据：依赖清单、能力/测试矩阵、来源锁和基线结果。BM0 完成仅表示范围已冻结。

## BM1 分发模型与选择契约

任务树：定义 SkillPackage → 定义业务/系统集合及锁 → 定义目标平台/模式与 Transport 规则 → 定义安装选择/归属模型 → 定义兼容旧 catalog 的方式。

验收标准：

1. skill 元数据具有 ID、版本、目录、描述、系统/架构范围、资源来源、外部程序要求和内容摘要；集合元数据具有 ID、版本、明确成员锁及适用条件。统一发布节奏下仍保留每个 skill 的独立版本字段。
2. 标准 SKILL.md 的可发现性不依赖自定义字段。发布时如需将本仓库扩展字段移到旁置元数据，必须验证 Kai 所需信息完整保留且由消费层正确读取。
3. 所有公开索引和旧 catalog 兼容视图来自唯一声明；有 schema 版本和对应读取器测试。旧 catalog 消费者不可因增加新字段而未经验证地继续宣称兼容。
4. 固定清单输入，分别解析单 skill、development、software-management、五系统两模式，得到预期且去重的成员/Transport；Kai 使用自身 Transport 时不叠加第三方连接 skills。
5. 缺成员、重复 ID、循环集合引用、摘要冲突、目录越界、不支持的平台/模式组合均返回非零；无目标写入。
6. 同一业务 skill 可安装而目标设备尚未连接；执行前必须确定目标事实。系统全量选择必须显式给出系统和执行方式，控制端系统不能替代目标系统。
7. 无目标网络或内部工具时，集合的“可安装”不等于业务的“可执行”。外部程序和服务条件在计划中明确，不由集合解析器偷偷安装。

交付证据：schema、代表性清单/锁、选择行为测试、兼容性决策记录。

## BM2 单 Skill 自包含

任务树：抽取必要公共执行资源 → 封装各 skill 本地路径 → 内嵌必要平台资源和首次引导 → 修正独立说明/引用 → 从孤立目录运行。

验收标准：

1. 对六个通用 skill，分别只复制该 skill 目录到全新临时 skills 根目录；测试执行器看不到 canonical 仓库和相邻 skills，公开脚本的正常路径可运行。
2. skill 文档能独立说明任务入口、目标识别、程序前置条件和失败下一步。不要求模型先读取未安装的另一个 Kai skill；可选业务关联清晰标注。
3. 必需资源位于本 skill 内，路径含空格和中文、移动目录、独立 shell 调用仍正确。公共资源可追溯到唯一源码；没有运行时访问构建机绝对路径、源码 symlink 或 sibling checkout。
4. 六个 skill 各覆盖一个有可观察结果的成功用例，以及缺工具、工具冲突、原生命令失败等适用负向用例。mock 只证明调用契约，不能替代后续真实软件任务。
5. kai-project-dependencies 在没有 kai-dev-environment 目录时仍能检查 SDK 并完成已具备运行时的依赖任务；缺 SDK 时使用自身携带的引导能力或准确报告下一步。
6. kai-storage-files 的空间/搜索正常路径不因未安装开发环境 skill 而失败；下载业务不因缺少可选 iStoreOS 诊断 skill 而无法执行。
7. Windows 没有 Bash 时，可以从独立包内的原生说明及 PowerShell 引导入口开始；已有 Bash、jq、mise 的复用行为正确。计划/发现不隐式启动 KSpeeder 服务。
8. 每个公开平台专属 skill 同样满足目录闭包；Transport skill 可以单独发布，但不带入无关系统维护策略。必需的嵌入脚本不会因带有 SKILL.md 而被二次发现。

交付证据：孤立目录行为测试、资源闭包和来源摘要、独立说明检查。

## BM3 独立产物与集合生成

任务树：扩展声明驱动生成器 → 输出 skills 目录 → 生成业务集合锁 → 生成系统全量及兼容预设 → 校验一致性和成员覆盖。

验收标准：

1. 所有 BM0 标记为公开的业务/平台/Transport skills 均可生成独立目录；每个目录有根 SKILL.md、必要资源及来源清单。
2. development 至少包含开发环境、项目依赖、下载加速；software-management 至少包含软件管理、下载加速。是否将 bootstrap 作为额外可发现成员由清单明确声明，不因代码依赖自动展开其他业务入口。
3. 系统全量生成结果等于“本发行版本兼容该系统的全部公开业务 skills + 该系统专属 skills + 本执行方式需要的连接 skills”；用集合相等断言验证，不能只检查若干名称存在。
4. 五系统各有两种模式，共十个预设。平台专属 skill 不进入不兼容系统；on-device 不附带远控入口；远控连接能力按目标系统选择。
5. 同一 ID/version 的 skill 在独立目录、业务集合、系统集合和旧 preset 内文件级摘要一致。集合包装层可以不同，skill 内容不随集合改变。
6. 生成器拒绝缺失资源、非法来源/输出路径、来源符号链接和重复活跃 ID；不覆盖非本工具生成的用户目录。
7. 同一 checkout 生成两次，文件列表与摘要一致；生成校验能检测手改产物、漏生成和资源过期；删除源码 checkout 后生成产物仍可使用。

交付证据：全部成员锁、内容比较、生成一致性和脱仓库运行结果。

## BM4 统一安装与选择

任务树：扩展 list/describe → 接入 skill/bundle/platform-all 选择 → 生成完整 dry-run → 复用事务安装入口 → 提供离线安装和 Windows 首次入口。

计划接口示例（实施前不能当作已有命令使用）：

```sh
sh install.sh --skill kai-download-acceleration --consumer codex --dry-run
sh install.sh --bundle development --consumer codex --dry-run
sh install.sh --platform windows --all --mode on-device --consumer codex --dry-run
```

验收标准：

1. 三种选择均有可读和 JSON 的 list/describe/plan；未知 ID、互斥选项及不完整的系统全量选择明确失败，不扩大为安装所有系统。
2. dry-run 给出选择、目标目录、锁定版本/摘要、实际新增/复用/冲突内容以及 Transport；前后目录/归属/配置摘要相同，目的目录原本不存在时仍不创建它。
3. Codex、OpenCode、generic 的目的路径选择正确，显式目录优先；测试只写隔离目录。下载/安装 skill 与在目标设备安装程序的动作分别报告。
4. 单 skill 安装只激活一个所选业务入口；必要资源内嵌而不自动激活额外业务 skills。集合安装的实际活跃列表与计划精确相同。
5. 单 skill 直接复制无需本仓库安装器；受管归属/升级由安装器负责。手工复制目录与受管目录在状态输出中可区分。
6. 离线归档提供其选择所需的完整资源，不临时回源仓库拼依赖；离线安装不误报为在线下载通过。
7. Windows 原生入口可先展示计划和定位 Bash，再进入安装；不选中 WSL bash，不要求先调用尚未存在的 Bash 脚本才能看到下一步。
8. 旧 --platform/--mode、--profile 的既有有效调用继续选中明确兼容集合；提示准确，现有查询输出兼容性按 BM1 冻结的合约验证。

交付证据：CLI 端到端行为测试、dry-run 零写入对照和离线安装结果。

## BM5 共存、升级和卸载

任务树：记录单装/集合选择意图 → 按 ID/version/digest 共享安装内容 → 实现变更事务及锁 → 处理冲突和升级 → 验证卸载与故障恢复。

验收标准：

1. “单装 A → 安装含 A 的集合 B → 卸载 B”保留 A；“安装 B → 单装 A → 卸载 B”同样保留 A。反向卸载顺序也正确。
2. 两个集合共享 A，卸载其中一个仍可执行 A；释放最后一个受管选择后才删除未修改的受管 A。重复安装/卸载幂等，不重复累加归属。
3. 同 ID 同版本同摘要复用；同 ID 同版本不同摘要拒绝；不同版本影响其他选择时，在写入前列出冲突。显式升级必须同步更新全部受影响的选择锁，否则停止并保留原状。
4. 集合升级增删成员后，只回收没有其他选择使用的旧成员。单装/另一个集合的成员版本和选择意图不丢失。
5. 用户修改的文件、外来同名目录、失效或改变目标的链接和不可信归属记录均保留并返回冲突；既有 --force 不能绕过其他选择锁或吞掉修改内容。
6. 注入解包失败、安装前失败、交换中失败和取消，均保持旧可用状态或可确定地恢复；状态记录与实际文件一致，无半安装集合。
7. 两个进程同时操作同一目的目录时串行化或有一个明确失败；不能丢失选择、把新内容删除或产生半写入清单。锁持有进程异常退出后的恢复可测试。
8. 验证 copy 与继续支持的 symlink 模式；源目录内容变化必须被检测，不能以“相同 ID”认定内容可信。若某组合不支持 symlink，写入前明确拒绝。
9. 无关 skill、用户项目和软件运行数据保持；卸载 skills 不卸载 mise、ks-cli、KSpeeder 服务或业务软件。

交付证据：共存场景表、文件/归属前后摘要、故障注入、并发和恢复结果。

## BM6 历史迁移与消费者兼容

任务树：冻结真实历史安装样本 → 迁移旧 preset 归属 → 保持 ID/别名兼容 → 验证通用 Agent 加载 → 同步 Kai canonical 资源及来源锁。

验收标准：

1. 从固定历史提交生成安装样本，不用当前 HEAD 假装旧版本；分别迁移到单 skill、业务集合和系统集合。旧 preset 记录转成等价选择，成员不重复、不丢失。
2. 同时存在多个旧归属记录时正确合并共享内容；不一致摘要、旧用户修改或无法判定的所有权停止迁移，保持原文件及记录。
3. 迁移后可升级和卸载；注入迁移中断可恢复。旧 alias 仍只指向一个活跃新 ID，不重新激活四个已退役 iStoreOS 主入口。
4. Codex、OpenCode、Reasonix 的实际发现/loader 测试分别覆盖独立目录和集合：名称、描述、脚本路径正确；不要求支持本项目扩展字段才能发现基本业务。
5. “安装 Python”“npm ci”“下载文件”“查询空间”“修复 LuCI”等冻结输入选择正确入口；通用技能不因内嵌 bootstrap 文档被错误路由到工具安装。
6. Kai 继续使用 canonical System Pack 和自身 Transport。公共代码重构后 vendor、source lock、资源路径及运行测试同步，不能只验证第三方目录。

## 执行、优化与结果记录

依赖顺序为 BM0 → BM1 → BM2 → BM3 → BM4 → BM5 → BM6 → BM7/BM8 → BM9 → BM10。BM7/BM8 可以独立推进；这一依赖关系不要求启动多个 Agent。

每个里程碑开始时输出本阶段任务树和 case ID/预期；实现后运行相关行为测试及受影响回归。初次自检失败后最多优化三轮，每轮保留失败、根因、变更、测试结果和原生资源清理记录。三轮后仍有 required 失败，停止依赖该门禁的自动推进，报告准确阻塞；只有新的明确授权才能开始专项修复。独立分支可继续的工作不被虚报为 blocked。

状态至少区分 planned、running、passed、failed、blocked、awaiting-release；具体 case 另记录 passed/failed/blocked/skipped。required 的 skipped 不计通过，外部网络失败也不以静态检查替代。

证据记录必须能回答：测试哪个 case、哪份 skill 内容/资源摘要、哪个系统/架构、什么执行模式、实际命令/结果、是否修改目标、如何清理。私有配置保存在仓库外，公共报告引用可审查摘要。

本机 Go/npm/Cargo/Zig 安装、构建或测试沿用 SSD 缓存入口；远程测试使用各自可验证的持久目录。计划阶段不需要构建 SDK 或修改远端服务。
