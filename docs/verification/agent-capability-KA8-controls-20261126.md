## 开测前的任务树与验收标准

1. 优化一 / round13：核对脚本事实保真与 QA/生产读取器差异。
   - 对三张冻结服务卡实际执行 canonical `service.inspect`，对照配置、登记、运行态、日志原文及文件指纹。
   - 对照 QA 字节窗口与生产行窗口；通过实际 Agent 集成测试验证读取快照、envelope 和路径边界，不暴露 shell、私有配置或外部文件。
   - 在授权原生机只读检查默认采证覆盖；所有不足明确记为 partial/unknown。
   - 自检：夹具保真通过；原生默认覆盖未通过。新 QA 适配器丢失 envelope 的集成测试先红后绿，付费读取器对照在修正后才开始。它是本轮 QA 适配错误，不是部署版 KaiPlus 的已证实故障。
2. 优化二 / round14：完全固定证据，分离获取过程与解释过程。
   - 两个现有授权模型配置 × C02/C11 × 三次重复，共 12 个会话。
   - 原始文档按路径排序，以字节不变的 JSON 附件交付，无工具；系统/用户/工具初始输入在每张卡内一致。不得删掉失败或截断样本。
   - 自检：全部附件与原文一致；11 个完整回答中 5 个核心通过、6 个失败；另 1 个末尾 length，不评推理。
3. 优化三 / round15：只替换通用读取器接口，保留 canonical 查询及同一任务。
   - 两个配置 × 两张卡 × QA 读取器/生产 `read_file` × 三次重复，共 24 个会话。
   - 转发生产 ReadEnvelopeProvider、ReadPathResolver、SnipHinter；允许的原始文档路径映射到拥有的夹具目录。
   - 记录实际获准请求中的消息内容哈希，审计关键文本是否进入后续请求；以真实 OpenAI 适配器和本地 HTTP 接收端验证哈希与 wire 内容对应。
   - 自检：关键文本 24/24 进入获准请求，零来源窗口错配；23 个完整回答中 20 个核心通过、3 个失败；1 个超时且缺权威 usage，不评推理、不重跑，完整保留费用上界。

每次的输入、二进制和代码哈希均已在开测前冻结。原始卡 revision4 的哈希保持 `db225bf2b937c8f51fcb60feacd69328a80a917bb307214972ecfd427f41bdc7`。

确定的模型侧错误包括：

- 固定完整证据仍有 C11 回答把失败归给未被观测调用的 `native.Check`，或声称“失败发生在守卫放行之后”。工具获取不全不是这些样本的充分解释。
- 生产读取器 C02 的一次回答明确断言“现在这套状态是迁移中途或回退未完成的残留，却被标成了 active”。现有数据只支持路径不同；空格路径、不同阶段/范围的摘要和 active 不能证明这个状态。
- 两个读取器 C11 回答的核心失败属于未解释实际 direct init/procd 链的反证遗漏；并未据此声称它们明确编造了当前守卫执行。

读取接口改变了调用数与时间分布，但没有建立可靠的准确率提升。实际生产读取器具有行号、行窗口、快照、提示与不同工具 schema；这组比较不能把效果归给单一窗口参数。两个配置的思考默认值也不同，网关实际采用的深度/权重没有独立核实，因此不能给模型品牌排名。

## 已确认的工程问题与修复

1. **QA 与生产读取语义不同。** QA 默认 2048 字节、最多 4096 字节且 JSON 包装；生产默认 2000 行、带行号和读取快照。这轮新增 opt-in 对照和测试，不改变产品默认行为。
2. **旧“已交付”审计缺少请求证据。** 过去 40 个样本只验证会话中的工具消息，不能单靠它证明消息经过裁剪后仍进入请求。本轮 24 个读取器样本新增获准请求哈希。其关键文本全部匹配；12 个固定证据样本另有完整附件一致性检查。获准发送不等于请求已完成，超时仍不评分。
3. **实际原生查询覆盖不足。** 默认登记文件超过 2048 字节后为 `hasMore:true/content:null`；原生 logread 超过 4096 字节后 logs 为 unknown，当前没有针对这份命令输出的稳定分页引用。它诚实报告 partial，没有证明一次查询能交付所有关键事实。KA8-T01 原来的夹具通过证据保留，原生覆盖门槛改记失败。
4. **凭据脱敏会吞掉相邻 JSON 字段。** 紧凑 JSON 的 token 字段位于前面时，旧 sed 删除后面的 phase/target，仍报 succeeded；转义字段名也能避过字面匹配。这是合成凭据复现，不声称生产密钥发生泄露。修复使用已有 jq 逐字段递归脱敏，标记 `redacted:true`；解析器缺失、敏感 JSON 不完整或多文档时返回 unknown/`REDACTION_UNAVAILABLE`，不安装依赖。URL `key`/`auth` 参数也有红到绿回归。

第 4 项在 36 个模型样本全部结束后才改 canonical，并重新生成独立包、平台副本和集合锁。三张原始无密钥服务卡的新旧回执除观测时间完全一致，文件未变；因此它不解释这些无密钥样本中的错误，也不能把旧模型结果当成修复版全链路验收。

最终代码的能力测试 **87 项通过**，QA Go 包通过，生成物一致性与 diff 检查通过。原生机没有 jq：两个敏感 JSON 合成来源明确 unknown，普通 JSON 事实原样保留；系统 init/config/登记指纹未变，拥有的 `/tmp` 阶段目录已删除。最终默认查询仍为 partial：真实生成配置含 JSON 转义，在这台无 jq 机器上也变成 unknown。这是保守解析要求带来的采证完整性退步，不能称为原生可用性验收通过。原生成功解析脱敏分支尚未验证，完整平台矩阵未执行。
